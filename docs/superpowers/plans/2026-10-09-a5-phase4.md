# A5 phase 4: Google OAuth

Implement the approved phase 4 scope in the existing `codex/a5-auth` checkout.
Preserve commit `58bf30e`, the shared User, local campus verification and fixed
permissions. No push/deployment, new charts, or automatic phase 5 execution.
The user requested necessary targeted tests and no repetitive stage reviews.

1. Replace the GIS credential POST with allauth's Google authorization-code
   login/callback. Configure the provider from environment credentials, enable
   PKCE, retain POST/CSRF initiation and allauth session-bound state checks.
   Expose only the required provider endpoints, preserving the custom account UI.
2. Add a social adapter enforcing a verified Google campus email and a stable
   Google subject. New users retain unusable passwords and must complete the
   existing six-digit campus challenge before a second Google login establishes
   a session. Provider verification does not grant campus access.
3. Reuse linked accounts by subject. Bridge existing legacy subject links after
   matching email/account checks. Reject anonymous same-email merges. Permit an
   explicit connect flow only from an already qualified user, to the same email,
   without stealing another user's Google identity.
4. Replace token JavaScript with server-rendered OAuth POST buttons. Add a small
   explicit connect section to existing Settings. Return useful cancellation,
   provider failure and account-conflict feedback without exposing credentials.
5. Replace obsolete token tests with simulated authorization-code round trips,
   testing state/replay, CSRF, PKCE, new/repeated/legacy accounts, campus gates,
   safe redirects, conflicts and explicit connection. Run affected auth/access
   regression, Django checks and diff checks; distinguish this from real Google.
6. Append key changes/reasons only to the consolidated weekly note. Defer
   operational/manual/deployment documentation to phase 5, as requested.

Real Google validation requires credentials in ignored local `.env`, registered
redirect URIs and a campus Google test account. Never request secrets in chat or
persist SocialApp credentials/tokens in tracked SQLite. No migration is required
for this stage because the allauth tables were added in phase 2.
